# 社区养老管家 Agent 方案

> 状态：设计基线，未实现
> 更新时间：2026-11-26
> 适用范围：员工端、管理后台；家属端为后续评估
> 管理端交互稿：[Agent管理端交互图.md](Agent管理端交互图.md)
> 数据底座：[Agent数据底座概要设计.md](Agent数据底座概要设计.md)
> 设计稿：[Agent能力设计稿.md](Agent能力设计稿.md)

## 1. 结论

平台已经跑通「家属下单 → 管家确认/派单 → 员工接单/记录/完成 → 家属确认/评价」的完整链路。

Agent 的价值不在于给每个角色配一个聊天机器人，而在于把链路上**高频、手工、易出错**的环节变成 AI 辅助。因此本方案不再按「家属端 / 员工端 / 管理后台」三个角色切分，而按**能力**切分：

- **P0**：员工服务记录助手（页面内嵌，最高优先级）
- **P0.5**：数据地基（员工排班/容量、候选接口、定时任务）
- **P1**：管理端派单建议 + 异常巡检
- **P2**：家属服务顾问（视转化目标再启动）

明确不做：老人端 Agent、纯查询聊天、自动执行写操作、自然语言报表。

## 2. 为什么不做三个角色 Agent

| 问题 | 具体表现 | 后果 |
|---|---|---|
| 按角色切，而不是按任务切 | 三个 Agent 的工具表高度重叠，都是 list/detail 包装 | 三套会话、三套 prompt、三套评测，成本 ×3，价值不清晰 |
| 只读能力是已有 UI 的复读 | 家属查订单已有订单列表/详情；员工今日任务已有工作台；管理员待派单已有订单页 | 用户不会从一键页面切换到打字 |
| 号称「推荐」，但缺少推荐所需数据 | `StaffProfile` 只有 skills/rating，没有排班、容量、可用时间 | 派单「推荐」退化成「是否同站点有在岗员工」 |
| 主动能力缺少基础设施 | 无定时任务；通知只落库不推送 | 异常提醒、巡检、催收都落不了地 |
| 聊天形态与现有交互冲突 | 家属下单已经是芯片式 4 步；员工工作台已有一屏统计 | 加聊天是倒退，不是提效 |

## 3. 三条硬边界

1. **不做医疗诊断**
   - 不判断病情、不建议用药、不解释检查报告。
   - 紧急情况固定引导拨打 120 或联系社区管家。

2. **不做无确认的资金和权限操作**
   - Agent 不能直接退款、改价、派单、停用账号。
   - 涉及写操作必须走「Agent 提议 → 用户确认 → 后端执行」。

3. **不跨角色越权**
   - 家属只能看自己绑定的长辈和订单。
   - 员工只能看派给自己的订单和服务对象。
   - 管理员能力单独控制。
   - 权限判断必须在后端完成，不能相信前端传来的角色。

## 5. 能力评估矩阵

按「频率 × 人工成本 × AI 相对规则的增量 × 风险 × 数据就绪度」评估。

| # | 能力 | 端 | 形态 | 频率 | 人工成本 | AI 增量 | 风险 | 数据就绪 | 建议 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 服务记录代写/润色 | 员工 | 页面内嵌 | 高 | 高 | 高 | 低 | 高 | **P0** |
| 2 | 服务前注意事项摘要 | 员工 | 页面内嵌 | 高 | 中 | 中 | 中（医疗边界） | 高 | **P0 附带** |
| 3 | 员工窄问答（这单注意什么/怎么写） | 员工 | 对话 | 中 | 低 | 中 | 低 | 高 | P0 最小入口，不做通用助手 |
| 4 | 派单候选 + 解释 | 管理 | 工作台 + 对话 | 中 | 高 | 中（规则占 80%） | 中 | 低（缺排班/容量） | **P1，先补数据** |
| 5 | 异常巡检（超时/未派/未付/缺记录） | 管理 | 后台队列 | 中 | 高 | 中 | 低 | 中（需定时任务） | **P1** |
| 6 | 运营自然语言报表 | 管理 | 对话 | 低 | 中 | 低 | 低 | 低 | 不做，先补 BI |
| 7 | 家属服务顾问（该买什么/FAQ） | 家属 | 对话 + 内嵌 | 中 | 中 | 高 | 中（不承诺疗效） | 高 | P2，视转化目标 |
| 8 | 家属查订单/查记录问答 | 家属 | 对话 | 中 | 低 | 低 | 低 | 高 | **不做**，已有页面 |
| 9 | 老人端语音管家 | 老人 | 对话 | 低 | 高 | 高 | 极高 | 低 | **不做** |
| 10 | 尾款催收 Agent | 管理 | 对话/队列 | 低 | 中 | 低 | 高 | 中 | 不做 Agent，可做规则队列 |
| 11 | 自动确认/自动派单/自动退款 | 全部 | — | — | — | — | 极高 | — | **不做** |

关键判断：

- 第 1 项是唯一「高频 + 高人工 + 高 AI 增量 + 低风险 + 数据现成」的能力，应第一个落地。
- 第 4 项业务价值高，但系统缺排班/容量/可用时间，AI 无法真正排序，必须先补数据。
- 第 7 项是家属端唯一有价值的 AI 能力，但当前优先级不高，放 P2。
- 第 6、8 项是典型的「为了 Agent 而 Agent」，直接砍掉。

## 6. 能力设计

### 6.1 P0 员工服务记录助手

**目标**：把「每单必做、纯手写、质量参差」的服务记录，变成「员工写两句话 → AI 生成规范草稿 → 员工改完提交」。

**落点**
- H5：`apps/h5/src/views/StaffRecordPage.vue`，在记录 textarea 上方加「AI 帮我写」。
- 小程序：`apps/miniapp/pages/staff/record.*`，同位置加按钮。
- 不新增页面、不新增聊天入口、不改变接单/开始/完成的现有流程。

**输入**：员工随手写的要点 + 订单上下文（服务名、时间、老人健康备注、订单备注、照片数量）。
**输出**：固定结构的记录草稿（服务内容 / 医嘱记录 / 下次安排 / 家属沟通 / 照片数），回填 textarea，员工可改。

**硬约束**
- 只生成草稿，**不自动提交**；提交仍走现有 `POST /orders/{id}/records`。
- 不做诊断、不解释检查结果、不建议用药；医生的话只能以「医生反馈」转述。
- 上下文最小化：不把手机号、完整地址塞进 prompt；照片不传原图，只传数量。
- LLM 不可用时按钮隐藏或降级，不影响现有流程。

**附带能力**：把老人健康备注压成「本次服务注意」清单（如：糖尿病需提醒用药、独居、行动不便），明确标注「来自档案，不构成医疗建议」。

**技术形态**：单轮、无会话表、无多工具循环；一次 prompt + 一次返回，成本最低。只通过 `ElderService` / `OrderService` 读权限内数据。

### 6.2 P0.5 数据地基

这些不是 AI，但决定 P1 能否成立：

1. **员工可用性**：工作时间、每日容量、请假/停用。挂在 `StaffProfile` 上或独立表。
2. **候选查询接口**：`GET /api/v1/admin/orders/{id}/candidates`，同站点 + 技能匹配 + 可用 + 当前负载 + 评分。
3. **组合动作接口**：`confirm + assign` 一个事务，避免前端串两个请求造成「已确认未派单」。
4. **定时任务框架**：一个轻量 worker（独立容器或 cron），先跑只读扫描。

具体表结构、接口、迁移、验收和实施路线见 [Agent数据底座概要设计.md](Agent数据底座概要设计.md)。

### 6.3 P1 管理端派单建议

- **候选来自规则引擎，不是 LLM 自由发挥**：
  1. 同站点、在职、staff 角色；
  2. 技能匹配服务类目；
  3. 当前活跃派单数（assigned + accepted）；
  4. 评分。
- LLM 只负责把规则结果转成「为什么推荐」和风险提示。
- 必须显式暴露数据缺口：「当前未接入排班，无法判断预约时间是否请假」。
- 写操作仍由管理员点「确认并派单」触发，二次确认，全量审计。
- 无候选时给具体原因（无同站员工 / 技能不匹配 / 已满负荷），不硬派。

### 6.4 P1 异常巡检

- 定时扫描：待确认超时、已确认未派、已派未接、服务中超时、已完成有尾款、已完成缺记录。
- 结果进入管理端「待处理队列」，靠角标/列表呈现，**不依赖推送**。
- LLM 只负责生成人话解释和建议动作，不自动执行。
- 无定时任务前，先提供按需查询接口，不阻塞 P1。

### 6.5 P2 家属服务顾问

- 入口放在小程序/H5 首页「联系管家」附近，不新开聊天 Tab。
- 能力边界：根据老人档案和服务目录推荐服务、回答价格/包含项/取消规则、引导转人工；不承诺疗效、不做诊断。
- 只有把「家属转化与自助」提为首要目标时再启动。

### 6.6 明确不做

- 老人端 Agent。
- 家属/员工的纯查询聊天（已有页面，做了是倒退）。
- 管理端自然语言报表（先把 Dashboard/BI 补好）。
- 三套独立聊天 Agent、三套会话与评测。
- 自动退款、改价、派单、停用账号。
- 尾款催收 Agent（可做规则队列，不做对话）。

## 7. 架构设计

```text
H5 / 小程序 / 管理后台
        │
        ▼
POST /api/v1/agent/*
        │
        ▼
modules/agents/router.py
        │
        ▼
modules/agents/scenarios/*.py
  ├─ 组装当前用户上下文
  ├─ 调用 LLM
  ├─ 解析结构化输出
  └─ 返回草稿/建议
        │
        ▼
modules/agents/tools.py
  └─ 调用现有 service 层
        │
        ▼
OrderService / ElderService / CatalogService / StaffService
        │
        ▼
数据库
```

### 7.1 目录规划

```text
apps/api/app/modules/agents/
├── __init__.py
├── schemas.py       # 请求/响应、草稿卡
├── policies.py      # 角色权限、写操作白名单、医疗边界
├── prompts.py       # system prompt 和场景 prompt
├── tools.py         # service 封装，不直接查库
├── llm.py           # OpenAI 兼容客户端、超时、降级
├── candidates.py    # 派单候选规则排序
├── router.py        # /agent/* 接口
└── scenarios/
    ├── record_assist.py     # P0
    ├── prep_brief.py        # P0
    ├── dispatch_suggest.py  # P1
    ├── anomaly_scan.py      # P1（定时任务调用）
    └── family_advisor.py    # P2
```

### 7.2 关键原则

- **工具只调用 service，不直接查库。**
- **工具入参和出参都走 schema 校验。**
- **所有 Agent 动作记录到审计日志。**
- **LLM 不可用时不影响主业务，前端降级为普通页面入口。**
- **规则负责事实与候选，LLM 负责表达与解释。**

### 7.3 工具清单

| 工具 | 角色 | 类型 | 说明 | 阶段 |
|---|---|---|---|---|
| `get_order_context` | 员工/管理员/家属 | 只读 | 按权限取订单、老人、服务上下文 | P0 |
| `get_elder_profile` | 员工/管理员/家属 | 只读 | 取健康备注、社区、紧急联系人 | P0 |
| `list_services` | 全部 | 只读 | 查询上架服务 | P0/P2 |
| `draft_service_record` | 员工 | 草稿 | 生成服务记录草稿，不写库 | P0 |
| `draft_service_prep` | 员工 | 草稿 | 生成服务前注意事项 | P0 |
| `list_staff_candidates` | 管理员 | 只读 | 规则候选排序 | P1 |
| `explain_dispatch` | 管理员 | 只读 | 解释候选与风险 | P1 |
| `scan_anomalies` | 管理员/定时任务 | 只读 | 扫描异常订单 | P1 |
| `recommend_service` | 家属 | 只读 | 需求 → 服务推荐 | P2 |
| `escalate_to_human` | 全部 | 动作 | 转人工/联系管家 | P0 |

### 7.4 写操作必须两阶段

```text
用户：帮我写今天的服务记录
  ↓
Agent：返回记录草稿
  ↓
员工在页面修改并点击提交
  ↓
后端用 OrderService.add_record 写入
```

草稿阶段不写库；确认接口必须是独立请求，不能由 LLM 直接触发。

以下操作不开放给 Agent：

- 退款
- 改价
- 派单/改派
- 停用账号
- 删除档案
- 修改支付状态

这些操作继续走管理后台，保留人工判断和审计。

## 8. 数据与隐私

### 8.1 数据表

P0 不需要会话表，只需一张动作审计表：

```text
agent_actions
- id
- user_id
- role
- scenario        # record_assist / prep_brief / dispatch_suggest ...
- order_id
- payload         # 脱敏后的输入摘要
- status          # proposed / confirmed / rejected / executed / failed
- model
- latency_ms
- created_at
```

P1 增加：

```text
admin_tasks        # 异常巡检队列
- id
- type            # pending_timeout / unassigned / overdue / balance_due ...
- order_id
- severity
- status          # open / handled / ignored
- created_at
- handled_at
```

P2 做对话时再加 `agent_conversations` / `agent_messages`，不提前建。

### 8.2 隐私

- 上下文只放当前用户有权限的数据。
- 不把完整手机号、地址、健康备注塞进 system prompt；需要时通过工具按需取。
- 日志里对手机号、地址、健康备注做脱敏。
- 照片不直接传给 LLM，只传「有无照片/照片数量」。
- 对话默认保留 30 天，具体以隐私政策为准。

### 9.5 开关

`AGENT_ENABLED=false` 时：

- 不注册 `/agent/*` 路由，或统一返回 404/503。

- 不影响现有下单、派单、支付、记录流程。

## 10. Prompt 与上下文

System prompt 只放稳定规则：

- 你是社区养老管家助手，不是医生。
- 只处理当前账号权限内的数据。
- 不承诺治疗效果。
- 紧急情况引导 120。
- 不确定时转人工。
- 写操作必须走确认。

每轮上下文建议包含：

- 当前用户角色、姓名、所属区域。
- 当前页面/场景（员工记录页、管理订单详情）。
- 工具返回的结构化结果。
- 明确的「下一步可做什么」。

不要把整库数据或无关用户数据塞进 prompt。

## 11. 安全与评测

### 11.1 风险与对策

| 风险 | 对策 |
|---|---|
| 越权查询 | 工具内部复用 service 的权限判断，不靠 prompt |
| 提示词注入 | 用户内容只作为数据，不作为指令；工具白名单 |
| 幻觉订单/政策 | 关键信息必须来自工具结果；无结果就说不知道 |
| 误操作 | 写操作两阶段确认；支付/退款/派单不开放 |
| 医疗风险 | 固定话术拒绝诊断，引导就医/120 |
| 成本失控 | 每用户每日调用上限、超时、最大 token |
| 隐私泄露 | 上下文最小化、日志脱敏、保留期限 |
| LLM 故障 | 超时降级为普通页面/人工入口 |

### 11.2 验收指标

P0/P1 各准备 30 条真实问题做评测：

- 意图识别正确率 ≥ 90%
- 工具选择正确率 ≥ 90%
- 越权数据返回：0
- 无依据的订单/政策回答：0
- 医疗诊断/用药建议：0
- 平均响应时间 < 4 秒
- 单轮成本可控（按实际模型定价设上限）
- 无法回答时正确转人工

P0 额外指标：

- 记录草稿采纳率（直接提交或小改后提交）
- 员工写记录平均耗时下降
- 记录字段完整率提升
