## 1. 项目结构梳理

### 1.1 子项目一览（本次部署前三个）

| 子项目 | 技术栈 | 源码目录 | 构建命令 | 构建产物 | 运行依赖 | 端口 |
| --- | --- | --- | --- | --- | --- | --- |
| 后端 API | Python 3.12 + FastAPI + SQLAlchemy 2 + Alembic | `apps/api` | `docker build`（内部 `uv sync --frozen --no-dev`） | Docker 镜像 | PostgreSQL 16、MinIO | 8000 |
| 管理后台 | Vue 3 + Vite 6 + Element Plus | `apps/admin` | `pnpm build` | `apps/admin/dist`（base `/`） | 静态服务器（容器内 nginx） | 80（容器内） |
| H5 端 | Vue 3 + Vite 6 | `apps/h5` | `pnpm build` | `apps/h5/dist`（base `/h5/`） | 静态服务器（容器内 nginx） | 80（容器内） |

补充事实（来自代码，部署时按此对齐）：

- 后端所有路由前缀是 `/api/v1`（`app/api/router.py`），因此 Nginx **不能** rewrite 掉 `/api` 前缀。
- 管理后台与 H5 的请求基址都写死为相对路径 `/api/v1`（`apps/admin/src/api.ts`、`apps/h5/src/api/http.ts`），所以必须与后端**同域**部署，由 Nginx 分流；这样也天然规避跨域。
- 图片地址由后端返回 `/api/v1/files/<key>`；`FILE_DELIVERY=redirect` 时后端 302 到 `MINIO_PUBLIC_BASE_URL/<key>`，因此该地址必须是**浏览器可达**的地址（不能是 `minio:9000` 这种容器内网名）。
- 后端 `.env` 读取路径被锚定在项目根（`app/core/config.py` → `/app/.env`），镜像里没有该文件，容器部署全部走环境变量。

### 1.2 相互调用关系

```
admin/h5 (浏览器)  ──fetch /api/v1/*──▶ nginx ──▶ api:8000
api ──psycopg──▶ postgres:5432
api ──minio SDK──▶ minio:9000（上传写入）
api ──302──▶ 浏览器直连 minio:9000/<bucket>/<key>（读图，不占 API 带宽）
```

### 1.3 端口占用

| 端口 | 服务 | 暴露范围 | 安全组 |
| --- | --- | --- | --- |
| 80 | nginx 网关 | 公网 | 放行 |
| 443 | nginx 网关（配证书后） | 公网 | 后续放行 |
| 8000 | api | 仅 `127.0.0.1` | **不放行** |
| 5432 | PostgreSQL | 仅 `127.0.0.1` | **不放行** |
| 9000 | MinIO S3 | 公网（图片直链） | 放行 |
| 9001 | MinIO 控制台 | 仅 `127.0.0.1` | **不放行**，用 SSH 隧道 |
| 22 | SSH | 公网 | 建议限制来源 IP |

MinIO 控制台：`ssh -N -L 9001:127.0.0.1:9001 ubuntu@120.53.13.162`，然后本地开 `http://127.0.0.1:9001`。

## 4. Nginx：安装与配置

### 4.1 方案 A（推荐）：容器化 Nginx，不污染宿主机

`docker-compose.yml` 里的 `nginx` 服务即「安装」，无需 `apt install nginx`。配置文件已生成：

- `deploy/nginx/default.conf` —— 入口网关（挂载到容器 `/etc/nginx/conf.d/default.conf`）
- `apps/admin/nginx.conf` —— 管理后台容器内静态托管（含 `/assets` 长缓存、SPA 兜底）
- `apps/h5/nginx.conf` —— H5 容器内静态托管（同上）

关键路由原理：

| 规则 | 为什么要这么写 |
| --- | --- |
| `location /api/ { proxy_pass http://api:8000; }` | `proxy_pass` **不带 URI**，原始 `/api/v1/...` 原样透传，匹配后端前缀 |
| `location /h5/ { proxy_pass http://h5:80/; }` | 末尾带 `/`，把 `/h5/` 前缀**削掉**再转发。H5 构建产物里资源路径是 `/h5/assets/*`，容器内仍是 `/assets/*`，两层路径各自成立 |
| `location / { proxy_pass http://admin:80; }` | 后台 base `/`，其余路径全部归它，history 路由由容器内 `try_files ... /index.html` 兜底 |
| `location = /healthz` | 便于 `curl` 判定后端是否真的可用 |

上线前自检配置语法（容器起不来说明上游域名写错）：

```bash
cd /opt/socialoldcare
docker compose up -d nginx
docker compose exec nginx nginx -t
docker compose logs --tail=50 nginx
```

### 4.2 方案 B（可选）：宿主机 apt 安装 Nginx

不想用容器跑网关时：

```bash
sudo apt update && sudo apt install -y nginx
sudo systemctl enable --now nginx
```

静态产物按「目录名 = URL 前缀」摆放，**避免 alias + try_files 的路径坑**：

```bash
sudo mkdir -p /var/www/socialoldcare
sudo rsync -a --delete apps/admin/dist/ /var/www/socialoldcare/admin/
sudo rsync -a --delete apps/h5/dist/    /var/www/socialoldcare/h5/
```

`/etc/nginx/sites-available/socialoldcare.conf`：

```nginx
server {
    listen 80 default_server;
    server_name _;
    client_max_body_size 10m;

    # 后台：根路径
    location / {
        root /var/www/socialoldcare/admin;
        try_files $uri $uri/ /index.html;
    }

    # H5：/h5/ 前缀，root 指向父目录，路径自然拼成 /var/www/socialoldcare/h5/...
    location /h5/ {
        root /var/www/socialoldcare;
        try_files $uri $uri/ /h5/index.html;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 90s;
    }

    location = /healthz { proxy_pass http://127.0.0.1:8000/healthz; }
}
```

```bash
sudo ln -sf /etc/nginx/sites-available/socialoldcare.conf /etc/nginx/sites-enabled/socialoldcare
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

此时 compose 里只需 `docker compose up -d api admin h5`（不要起 `nginx` 服务，避免抢 80）。

### 4.3 域名与 HTTPS（可选）

1. 域名 A 记录指向 `120.53.13.162`，并完成 ICP 备案（`http://IP` 可先用，备案是后续接微信生态的前置条件）。
2. 证书可用 `certbot --nginx -d your.domain`（宿主机方案）或把证书挂进网关容器后加 443 server 块。

```nginx
}
```
（此时 9000 可收回内网，不再对公网放行。）

## 5. 后端部署

### 5.1 拉代码与生成 `.env`

```bash
sudo mkdir -p /opt/socialoldcare && sudo chown -R $USER:$USER /opt/socialoldcare
git clone https://github.com/AbrahamJay/old_carefully.git /opt/socialoldcare
cd /opt/socialoldcare

cp .env.example .env
openssl rand -hex 16   # → POSTGRES_PASSWORD（若复用旧库，改成旧库的真实密码）
openssl rand -hex 32   # → JWT_SECRET
vim .env
```

> 前提：远程仓库已有代码（`git ls-remote --heads origin` 能看到 `main`）。若本地还没提交/推送过，`git clone` 下来是空仓库，先提交推送，或用 rsync 直传（排除依赖与密钥）：
>
> ```bash
> rsync -az --delete \
>   --exclude node_modules --exclude dist --exclude .venv --exclude .git \
>   --exclude .env --exclude __pycache__ \
>   ./ ubuntu@120.53.13.162:/opt/socialoldcare/
> ```

`.env` 必须核对的三处：

| 变量 | 取值 | 坑 |
| --- | --- | --- |
| `POSTGRES_PASSWORD` | 复用旧 PG 时填**旧密码** | 新生成会导致认证失败；必须是 URL 安全字符（`openssl rand -hex`） |
| `MINIO_PUBLIC_BASE_URL` | `http://120.53.13.162:9000/socialoldcare-media` | 留空会退化成 `http://minio:9000/...`，浏览器打不开图 |
| `APP_ENV` | 默认 `prod` | `prod` 会强制 `ALLOW_DEMO_LOGIN=false`、`AUTO_SEED=false`、`JWT_SECRET ≥ 32 字节`；保留占位符会**启动失败**（这是有意的保护） |

### 5.2 让容器接入已存在的 PostgreSQL / MinIO

`docker-compose.yml` 里 `postgres`、`minio` 两个服务被放在 `infra` profile 下，**默认不启动**；复用旧容器时用 Docker 网络别名把它们「改名」成 compose 期望的名字。

> 前置：`docker network create socialoldcare-net`（第 3 节已做）。compose 把这个网络声明为 `external: true`，目的是让旧容器也能加入同一网络，同时避免 compose 重建/改名校验 label 时报错。

```bash
# 容器名以第 3 步 docker ps 的实际输出为准
docker network connect --alias postgres socialoldcare-net pg
docker network connect --alias minio    socialoldcare-net minio

# 验证：能从该网络里解析到这两个名字
docker run --rm --network socialoldcare-net busybox nslookup postgres
docker run --rm --network socialoldcare-net busybox nslookup minio
```

> 已在该网络时会提示 `already exists in network`，忽略即可。

特殊情况：

- **MinIO 是宿主机二进制安装（非容器）**：`.env` 改成 `MINIO_ENDPOINT=host.docker.internal:9000`，并给 compose 的 `api` 服务加
  ```yaml
      extra_hosts:
        - "host.docker.internal:host-gateway"
  ```
  同时确认它监听 `0.0.0.0:9000`（`ss -lntp | grep 9000`）。
- **服务器是空环境**，没有现成 PG/MinIO：跳过本节，用
  ```bash
  docker compose --profile infra up -d --build
  ```

### 5.4 Alembic 数据库迁移

默认 `AUTO_MIGRATE=true`：容器每次启动先跑 `alembic upgrade head`，版本已是最新则静默跳过。

手动执行 / 排查：

```bash
# 查看当前版本与最新版本
docker compose exec api alembic current
docker compose exec api alembic heads

# 手动升级（不启动依赖容器）
docker compose run --rm --no-deps api alembic upgrade head

# 只升级到指定版本
docker compose exec api alembic upgrade e70234af8edb

# 回滚一步（谨慎，涉及数据丢失）
docker compose exec api alembic downgrade -1
```

注意：`alembic.ini` 里没有连接串，`migrations/env.py` 直接取 `settings.database_url`，因此迁移用的就是容器环境变量里的库，**不会连错**。

### 6.1 构建产物与 base（关键差异）

| --- | --- | --- | --- | --- |

`apps/h5/vite.config.ts` 的生产 base 可用 `VITE_BASE` 覆盖（例如挂到 `/m/`）。`apps/admin/vite.config.ts` 保持默认 `/`。

### 6.2 容器化（本次采用）

```bash
cd /opt/socialoldcare
docker compose build admin h5
docker compose up -d admin h5 nginx
```

镜像内：`node:22-alpine` 构建 → `nginx:alpine` 托管。已新增 `.dockerignore`，避免把 macOS 的 `node_modules` 和本地 `dist` 拷进构建上下文。

### 6.3 开发期跨域 vs 生产同域

> 静态容器里的 nginx **只负责托管文件**，不再反代 `/api`；所有接口由入口网关的 `/api/` 转发。这样 admin/h5 容器启动时不需要提前存在后端，排查也更直观。

| 场景 | 请求路径 | 谁做代理 |
| --- | --- | --- |
| 本地 `pnpm dev`（admin:5173 / h5:5174） | `/api/v1/*` | Vite dev server → `VITE_PROXY_TARGET`（默认 `http://127.0.0.1:8000`），**不产生跨域** |
| 生产 | `/api/v1/*` | 网关 nginx → `api:8000`，同源，**不需要 CORS** |

因此：

- 生产环境**不要**把前端里的 `/api/v1` 改成服务器绝对地址；
- `CORS_ORIGINS` 只在「前端单独跑在别的域名/端口」时才需要配；
- 联调服务器后端时，本地写 `echo 'VITE_PROXY_TARGET=http://120.53.13.162' > apps/admin/.env.local`（h5 同理），该文件已被 gitignore。

### 6.4 备选：手工构建后上传静态文件

## 8. 日常运维

### 8.1 发布更新

```bash
cd /opt/socialoldcare
git pull
docker compose build api admin h5
docker compose up -d
docker compose ps
docker compose logs --tail=100 api
```

镜像带版本标签（`socialoldcare/api:0.2.0`），回滚时把 tag 改回上一版再 `up -d`；数据库回滚用 `alembic downgrade` 前先备份。

### 8.2 备份

```bash
# PostgreSQL
docker exec socialoldcare-pg pg_dump -U socialoldcare socialoldcare \
  | gzip > /opt/backup/pg-$(date +%F).sql.gz

# 复用旧容器时把容器名换成旧的（如 pg）
docker exec pg pg_dump -U socialoldcare socialoldcare | gzip > /opt/backup/pg-$(date +%F).sql.gz

# MinIO（容器部署时是 named volume，直接打包数据目录）
docker run --rm -v socialoldcare_miniodata:/data -v /opt/backup:/backup alpine \
  tar czf /backup/minio-$(date +%F).tar.gz -C /data .
```

### 8.3 日志与排障

```bash
docker compose logs -f api nginx                    # 实时
docker compose exec nginx tail -f /var/log/nginx/error.log
docker compose exec api env | grep -E 'DATABASE_URL|MINIO|APP_ENV'
```

| 现象 | 常见原因 |
| --- | --- |
| `network socialoldcare-net declared as external, but could not be found` | 未执行 `docker network create socialoldcare-net` |
| api 启动报 `生产环境 JWT_SECRET 必须为不少于 32 字节的随机值` | `.env` 里还是占位符，执行 `openssl rand -hex 32` 替换 |
| api 启动报 `生产环境必须关闭 ALLOW_DEMO_LOGIN` | `.env` 刚改成 staging 回滚残留；prod 下必须为 false |
| api 反复重启，日志 `connection refused` | PG 未接入 `socialoldcare-net`，或 `POSTGRES_HOST`/密码不对 |
| 网关起不来 `host not found in upstream "api"` | 先起 api/admin/h5 再起 nginx；`docker compose up -d` 一次起全即可 |
| 图片 404/无法显示 | `MINIO_PUBLIC_BASE_URL` 写成容器内网名；或桶未建（跑 `scripts/init_minio.py`） |
| 图片 403 | 桶策略未开匿名读：`init_minio.py` 不带 `--private` 再跑一次 |
| 后台登录后刷新 404 | 静态站缺少 `try_files ... /index.html`，检查 `apps/admin/nginx.conf` |
| H5 打开空白 | 访问了 `/` 而不是 `/h5/`（产物 base 是 `/h5/`），或网关 `proxy_pass` 少写末尾 `/` |
| `ZoneInfoNotFoundError` | 镜像缺 tzdata，确认使用本次更新后的 `apps/api/Dockerfile` |
